## 2. 用户需求与已经采用的设计

原有软件只有一组账号密码，多个地址可能属于不同账号，容易用错误的登录状态打开下一条地址。此次需求包含：

1. 为不同账号分别保存名称、平台、账号和密码。
2. 每条地址选择自己的账号，按地址顺序执行。
3. 账号之间隔离登录状态，修改凭据后重新登录。
4. 登录失败或出现验证时不无限等待；等待时限可在设置中修改。
5. 超时跳过当前地址，继续下一条；“停止”必须及时中断正在等待的任务。
6. 三个平台登录需要分别核对，不能用一站的测试代替另一站。

采用顺序队列，未新增多账号并发、后台无限重试或失败地址自动回头补跑。这样更容易保证页面、凭据和当前任务对应，也符合最小改动要求。

## 3. 多账号配置与地址绑定

### 配置结构

`coursemate/config.py` 的 `Config.accounts` 将旧 `[account]` 转成固定的 `default` 账号；新增账号使用 `[[account.list]]`，每项包含：

| 字段 | 用途 |
| --- | --- |
| `id` | 稳定标识，地址绑定和登录状态索引用它 |
| `name` | 界面显示名称，可以改名 |
| `platform` | 平台限制；空值允许按当前地址解析平台 |
| `username`、`password` | 该账号的凭据，仅保存在本机配置 |

每条 `[[course.list]]` 增加 `account_id`；旧地址未提供此字段时使用 `default`。

`coursemate/config_writer.py` 按固定模板写回 TOML，保留旧单账号配置兼容，并转义引号和反斜杠。`tests/test_multiaccounts.py` 用虚构凭据覆盖配置往返和特殊字符。

### 界面与执行

`coursemate/gui.py` 支持新增、改名、切换账号和逐地址选择账号。切换账号前先保存当前输入，切换后载入所选账号，避免两个账号的输入互相覆盖。

运行时，`runner.run()` 先解析地址的平台，再检查绑定账号是否存在、是否匹配平台。账号丢失或平台不匹配时跳过该地址并记录未完成，不能悄悄换成默认账号。

**经验：**显示名称不能作为账号身份。改名只更新显示，不应改变地址绑定或清空登录状态。移除账号前也要检查是否仍被地址使用。

## 4. 浏览器会话与登录状态隔离

`coursemate/browser.py` 的 `open_context()` 为当前账号建立浏览器上下文。切换账号时关闭旧上下文，再建立对应账号的上下文；可以复用浏览器进程，但不能复用另一账号的上下文。

登录状态使用 Playwright `storage_state()`，包含 Cookie 和站点存储，不只保存 Cookie。部分站点的登录依赖本地存储，只有 Cookie 的恢复方案可能不完整。

本机状态位于 `runtime/accounts/`。状态文件名依据账号稳定 ID，以及平台、用户名、密码的摘要生成：

- 不同账号分别存储。
- 修改平台或凭据后使用新的状态索引，旧状态不会直接套给新凭据。
- 文件名不直接使用用户名，也不会把账号 ID 当作目录路径拼接。
- 旧 `runtime/cookies.json` 保留，不自动归到某个新增账号；升级后首次可能需要重新登录。

**两个常见误区：**

1. 打开新标签页不等于隔离账号，同一上下文仍共享认证状态。
2. 哈希文件名不等于密码加密。配置仍可能包含明文凭据，状态 JSON 仍包含认证数据，均属私密文件。

`ensure_login()` 在再次确认登录后才调用 `persist_login()`。登录失败或超时不能把失败会话当成成功凭证保存。

## 5. 普通登录流程与平台差异

### 通用流程

```text
当前地址 → 解析平台 → 找到绑定账号 → 打开对应上下文
  → 检查登录状态
      → 已登录：复核状态
      → 未登录：打开登录页，填写该账号凭据，提交普通登录表单
  → 等待登录结果或人工操作
      → 确认登录：保存该账号状态，交给后续任务
      → 超时或失败：关闭当前上下文，跳过本地址
      → 用户停止：取消任务并收尾
```

凭据留空时保留人工登录入口。协议勾选须对应登录页明确的协议控件，并有当前任务授权；不能扩大到账号合并、绑定新身份等额外操作。

### 平台情况

| 平台 | 当前普通登录方法 | 必须注意的限制 |
| --- | --- | --- |
| 智慧树 | 等待 SPA 表单渲染，使用适配器内的账号、密码和登录按钮选择器；处理明确的协议复选框 | 登录页有重定向和页面变体。当前登录判据依赖域名，需要检查是否真的进入认证后的页面 |
| 学习通 | 普通入口与 v8 入口分别选择表单；v8 使用 `#uunnmm`、`#pwd`、`#login`，普通入口使用 `#phone`、`#pwd`、`#loginBtn` | 不能把 v8 页面套进普通入口；表单提交前页面可能已经被用户切换 |
| 智慧职教旧版 | 切到“账号密码登录”，按输入框提示填写，处理协议后提交；登录后的绑定提醒选择“下次绑定” | 目前地址路由只匹配旧版学习空间主机；单独输入 SSO 地址并没有完成路由适配和真实验收 |

智慧职教的登录成功判据还要求在旧版学习空间看到“我的课程”。看到新 SSO 登录页、出现验证控件，均不能证明这个新入口已经被任务队列支持。不能顺手把旧版课程、视频、文档能力扩大成新版全部能力。

### 登录成功不能只看表单消失

旧选择器在新页面找不到时，会天然得到“不存在／隐藏”；如果把它当作登录成功，容易带着未认证会话继续打开业务页面。

当前源码仍有需要后续审查的判据：

- 智慧树主要依据离开已知登录主机，不能由此保证所有重定向页都已认证。
- 学习通主要依据 URL、标题和 v8 可见登录输入框；异常分支存在返回已登录的宽松处理，不宜当作强认证证据。
- 智慧职教依赖特定主机和“我的课程”元素，新页面变体可能不满足。

这些是本次阅读发现的维护风险，本次只记入文档，没有修改。后续应使用用户授权的页面证据确认判据，不能单靠增加更多字符串判断宣称修好。

## 6. 可调等待时限、跳过与停止

### 设置含义

设置页“运行”中的“登录／验证等待（秒）”写入 `[runtime].login_timeout_seconds`，默认 `120`，至少 `1` 秒。

- GUI 拒绝非数字、非有限值和小于 1 的值。
- `Config.login_timeout_seconds` 遇到非法数值回退到 120 秒。
- 登录等待从 `ensure_login()` 开始计时，包含状态检查、导航、填表和等待，不是出现验证码才开始计时。
- 页面验证等待从工作协程检测到验证后开始。
- 登录循环重新读取等待配置；已启动的页面验证 `wait_for()` 使用启动等待时的时限，不能把两者的热更新行为混为一谈。

平台 `login()` 内仍有很长的等待循环，但正常执行路径由外层 `ensure_login()` 统一设置期限并取消，因此不能只看适配器循环长度就判断会无限卡住。绕开外层直接调用适配器时，也不会自动获得同样的期限保证。

### 超时后的行为

登录超时产生 `LoginTimeout`；页面验证超时产生 `VerificationTimeout`。地址队列关闭当前上下文，标记本轮未完成，继续下一地址，不自动回头重试。

`watch_address()` 同时监视课程任务、验证任务和停止状态。即使验证任务已在进入等待前失败，也应阻止当前地址继续运行，不能只等待下一次事件。

验证期间暂停播放和有效学习计时。超时退出时不抢先恢复视频，由地址队列取消任务并关闭会话，避免短暂继续播放造成状态混乱。

### 停止控制

`ensure_login()` 在等待前后检查停止，收尾时取消并等待登录任务及验证等待任务。仅在最外层循环检查停止不够：页面等待或适配器长循环会让停止失去响应。

取消后必须等待任务收尾，不能仅调用 `cancel()` 就假定没有后台操作。`tests/test_login_stop.py` 和 `tests/test_multiaccounts.py` 覆盖了这些关键行为。

## 7. 验证相关工作的状态与证据

当前工作区保留了本会话的验证处理试验模块。用户要求还原后，该模块与修改前记录的源码哈希一致。本次没有改动该模块，也没有重新运行真实验证。

本文只记录验证状态管理、人工接管、超时和验收缺口，不展开验证码答案识别或自动滑块操作的实现步骤。

| 观察到的现象 | 实际能说明什么 |
| --- | --- |
| 检测到可见验证容器 | 需要进入验证等待，不能视为通过 |
| 产生了页面操作或没有异常 | 只能说明执行过程，不能视为服务器接受 |
| 验证控件消失 | 可以结束对应的界面等待，但不能单独证明登录成功 |
| 验证接口明确接受 | 是验证环节证据，仍需确认认证后的页面 |
| 当前账号进入认证页面且身份正确 | 是登录证据，不代表课程进度或考试保存已验收 |

三站各 10 次新会话验收尚未完成；真实图片数字验证码样本仍待用户后续提供。不能把已有少量页面观察、离线 DOM 或历史试验日志写成这个验收目标已完成。

新会话必须区别于已有登录状态恢复；没有出现滑块而直接进入账号页面，不能算一次滑块通过。失败、超时、未出现验证、人工接管均应单独分类，不只统计最后的成功项。

## 8. 本次踩到的坑与可复用经验

### 8.1 一个账号配置套所有地址

问题是地址与凭据没有绑定，且共享登录状态可能把下一地址带到错误账号。

采用稳定账号 ID、逐地址绑定、独立上下文和状态文件。测试重点应是实际传入了哪个账号、恢复了哪份状态、是否关闭旧上下文；只有“配置能保存”还不够。

### 8.2 把空白页当作已登录

学习通过去可能把新开的 `about:blank` 当成已登录，导致填表根本不执行。当前先排除非 HTTP 页面，再检查登录入口特征。

经验是覆盖刚启动、仍在登录页、已跳转和异常页面四种状态，不能只测成功重定向。

### 8.3 同一平台不同入口使用不同控件

学习通 v8 与普通登录入口的账号字段、按钮不同。选择器需要由实际入口决定，不能以平台名称相同为由共用一套表单。

类似地，智慧职教 SSO 页和旧版学习空间是不同入口。页面能打开和平台路由能处理是两件事。

### 8.4 原生复选框与可见协议控件不一致

某些登录页隐藏原生 input，仅显示自绘协议框；点击协议文字又可能打开链接而不是勾选。

应区分明确复选控件、可见点击目标和协议链接。离线测试要覆盖隐藏 input 与自绘容器，并检查没有误点协议链接。

### 8.5 填表后页面已经变化

用户可能在程序填完后自行提交。继续无条件点击新页面中碰巧同名的按钮可能误操作。

学习通当前在点击前检查按钮存在且可见，页面已变时只等待结果。其他平台后续也应按真实证据审查同类竞态，不能在本次文档任务中顺手重构。

### 8.6 只在最外层加超时或停止

只有外围标记不能保证内部等待结束。需要取消实际等待任务，等待其收尾，并关闭当前账号上下文；下一地址必须重新建立正确状态。

登录错误、验证超时和人工停止应使用不同结果，避免“跳过了”被报告成“全部完成”。

### 8.7 验证消失后保留过长空档

验证可能刚消失又出现。旧的较长冷却会延迟再次检测；本次工作区改为正常轮询，不再额外空等半分钟。

回归不仅测第一次超时，还应测重复出现，以及暂停原因叠加时是否误恢复播放。验证码和弹题同时存在时，解除其中一个原因不能清掉另一个原因。

### 8.8 真实页面证据与本地测试混在一起

本地 route/DOM 可以验证字段、按钮、队列、取消和超时，但不能证明真实平台认证或保存。页面动作、控件状态、认证结果应分别记录。

故障记录公开时只保留泛化结论；截图、完整响应、会话信息和个人页面内容留在本机私密区域。

### 8.9 打包收口时扩大了修改范围

本会话为准备测试包调整过验证行为和文字，用户随后要求撤销。已经按该轮修改前状态还原，未将整个仓库重置到标签。

经验是先说明实际交付行为，避免将打包请求理解成可以重新定义功能；撤销时根据本轮改动或保存快照恢复，不用 `git reset --hard`、整体 `git restore .` 或 `git clean`，以免损失用户原有工作。

### 8.10 依赖可导入不等于 EXE 完整

源码环境安装模块不代表冻结包包含动态依赖。EXE 缺模块需要重新构建完整包，不能靠在 EXE 目录运行源码安装脚本修复。

本次没有新的包、启动截图或 ZIP 审查结果，因此不把源码依赖状态写成 EXE 验收。
