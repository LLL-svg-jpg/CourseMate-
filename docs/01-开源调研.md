## 二、三条技术路线对比

### 路线 A —— 浏览器脚本注入（代表：OCS）
在页面内注入 JS，直接操控 `<video>` 元素、监听弹题 DOM、调用搜题接口填答案。
- ✅ 用户能看见播放过程，"陪伴"形态天然成立
- ✅ 多平台适配成本最低（每平台一个 project 文件）
- ✅ OCS 是 **MIT**，可自由二次开发闭源分发
- ❌ 运行在页面上下文，易被前端反作弊探测

### 路线 B —— 外部浏览器自动化（代表：Autovisor）
Playwright/CDP 驱动真实浏览器，模拟点击。
- ✅ 不污染页面上下文，反检测优于路线 A
- ✅ 可无人值守、可托管到服务器
- ❌ 依赖 DOM 选择器，平台改版即失效
- ❌ 窗口最小化可能导致进度不累加（Autovisor 已知 Bug）

### 路线 C —— 纯协议模拟（代表：Samueli924/chaoxing、yatori-go）
不开浏览器，直接构造 API 请求上报学习进度。
- ✅ 最快最省资源，可批量、可 Docker
- ❌ **与"自动播放 + 陪伴"的产品定位不符**（根本不播放）
- ❌ 行为特征最明显，风控识别度最高
- ⚠️ chaoxing 为 GPL-3.0，传染性强，衍生代码不得闭源商用

## 三、结论

**主干选 OCS（MIT）**，理由：
1. License 最宽松，唯一可安全二次开发的多平台成熟项目
2. `packages/core/src/core/` 下已有 `answer-wrapper`（答案解析）与 `worker`（搜题调度），正是"出题→答题→继续播放"闭环的现成实现
3. `packages/scripts/src/projects/` 已按平台拆分（cx / zhs / icve / zjy / icourse / yuketang / unipus），新增平台是加文件而非改架构

**借鉴项**：
- Autovisor：反检测思路、视频暂停续播检测、异步协程弹题检测、Cookie 过期自动识别
- yatori-go：AI 大模型答题兜底、验证码识别、多账号调度
- destoryD/chaoxing-api：题库聚合层设计

**规避项**：
- 不引入 GPL-3.0 代码（chaoxing / WeBan / xxt），避免许可证传染
- 不做"暴力秒刷"（yatori 明确标注"会被检测到"）
