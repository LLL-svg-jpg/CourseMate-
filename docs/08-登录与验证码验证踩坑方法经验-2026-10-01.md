# CourseMate 登录与验证码验证：踩坑、方法与经验

> 整理日期：2026-10-01。本次维护和验证的交接记录。
> 只记录脱敏结论、源码位置、方法和复现步骤。真实凭据、配置、Cookie、题库、日志、截图、验证码图片及原始服务器响应均留在本机忽略目录，不进入本文或交付包。

## 1. 理解、假设、成功标准与边界

本次目标是智慧树、学习通、智慧职教三个指定登录入口分别连续完成 10 次全自动登录。智慧职教允许自动勾选隐私协议并新增阿里云拼图适配；学习通还须自动进入个人空间，真实复现一次即可。地址仍由用户填写，未新增“入口选择”界面。

采用的假设是：一次登录可以在原有最多三次本地验证操作内重试；同一会话最终必须认证成功，才能计入连续成功。不能跳过失败会话，也不能把不同批次的零散成功拼成 10 次。每次新会话的初始 Cookie 和站点存储必须为空。

成功标准分开检查：

1. 普通登录：对应账号字段填入、协议按授权勾选、提交及登录后必要跳转完成。
2. 验证码：真实服务器回执确认通过，不能只看图片对齐或控件消失。
3. 业务认证：业务登录回执、当前会话凭证、认证后的用户界面一致。
4. 窗口：实际请求最大化并检查窗口尺寸；默认窗口也另做真实登录复核。
5. 打包：前三站登录标准满足后才生成独立测试包，再检查包内模块、EXE 身份、启动和视觉。

没有推进真实课程、操作正式考试、调用付费模型、删除用户文件、覆盖旧包，或提交、推送、发布 GitHub。登录通过不能扩大解释成课程进度、考试或新版平台全部业务已验收。

## 3. 实际遇到的问题与修复方法

### 登录入口与认证判据

**智慧树：登录网关和成功页面可能同域。** 仅看离开旧登录主机，会把仍显示账号输入框的网关误认为已登录。修复为保留用户填写的指定网关入口，并排除仍可见的登录表单。真实验收另要求账号登录回执、会话凭证和认证后的用户信息。

**智慧职教：SSO 地址原来不被平台路由支持。** 新增对指定 SSO 登录路径的匹配，并保留用户所填入口。认证后可能留在 SSO 个人后台，而不是旧版“我的课程”页面；因此补充“后台路径、非空会话凭证、可见头像及个人资料表单”组合判据。真实验收进一步核对登录返回的用户身份与个人资料身份、会话凭证一致。单独进入后台 URL 仍不算成功。

**学习通：认证后仍需点击“进入个人空间”。** 菜单可能要悬停才显示，点击后会打开新标签。实现等待弹出页、把其个人空间地址转到执行器持有的原页面，再关闭本次弹出页，避免执行器继续持有旧页面。真实复现确认进入个人空间，且只保留一个页面。

**补充复核发现菜单有挂载延迟的风险。** 前一次真实复现通过，不能保证下一次不会漏点。后续默认窗口复核中，业务认证成功但个人空间未进入，先怀疑 `count()==0` 在菜单尚未挂载时直接返回。新增延迟三秒挂载菜单的回归，确实复现了这一风险；改为有限等待入口挂载后回归通过。这是普通登录后的导航问题，不能由验证码回执代替验收。

**真实漏点还包含重定向时序。** 只等菜单挂载后，真实复核仍漏点。进一步记录进入处理函数时的域名，确认当时仍在 v8，稍后才转到 v1 门户；原函数因域名不匹配提前返回。因此还需对 v8 等待门户重定向，再等待菜单挂载。增加重定向延迟回归，真实复核按“最终进入个人空间、仅剩一个页面”确认。这也说明不能把一个离线回归通过当作真实问题已经解决。

### 隐藏控件与初始化时序

**协议原生复选框尺寸为零。** 直接操作隐藏的原生控件会等待失败。改为点击可见的自绘复选框，再读取原生勾选状态确认。此操作来自用户明确授权；没有打开协议链接、绑定新身份或合并账号。

**“下次绑定”有隐藏和可见两个同名按钮。** 直接取第一个会命中隐藏按钮，造成验证码和业务登录都成功后仍卡住。改为遍历同名按钮并只点可见的一项，不选择“不再提醒”。

**预加载的验证码提示不等于正在验证。** SDK 可以提前把隐藏弹窗和提示文字放进 DOM。只查存在性或全文文字会一直误报有验证码。阿里云弹窗的检测改为可见性判断，保留其他已适配控件的检测方式。

**表单就绪不等于阿里云 SDK 就绪。** 实际遇到点击登录时拼图尚未初始化，按钮没有触发验证。仅在指定 SSO 页面存在 SDK 时，等待验证码图片完成加载后再点登录；等待受原登录超时与停止控制约束。

**采集时间不足也值得排查。** 阿里云 V2 官方文档要求脚本加载、初始化到验证请求间隔大于两秒。新增阿里云分支的可取消两秒等待。这一步曾改善个别会话，但单独增加等待仍未完成连续 10 次，不能把它当作唯一解决办法。

### 图像与坐标

**背景缺口被覆盖成平色，不能只匹配拼图 RGB 纹理。** 本地 OpenCV 使用透明度形成的轮廓，与背景边缘做相关匹配及轮廓距离比较；候选必须可靠且与第二候选有足够差距。图像歧义时刷新，不猜坐标。真实图片不进入测试文件；回归使用合成图片。

**透明边和外侧灰色描边会造成偏移。** 读取 alpha 蒙版的实际范围，并收缩一像素的外侧装饰边后匹配。合成回归覆盖有描边和重复缺口的情况。

**图片像素、CSS 像素和屏幕物理像素不能混用。** 目标先按图片自然宽度与实际显示宽度换算到 CSS 坐标。浏览器鼠标事件使用 CSS 坐标，不能额外盲乘 DPR。最大化会改变控件在页面中的位置，应每次读取实际包围框，不能写死屏幕坐标。

**手柄位移和拼图位移不是一比一。** 本次智慧职教的 300px 控件实测呈二次关系。先前沿用线性比率或拖动前探测的方案不能稳定通过；最终使用本机标定的二次逆解。当前只接受已标定的控件尺寸；未知缩放拒绝猜测。官方也不建议通过覆盖 CSS 改变拼图尺寸。

### 轨迹、回执与误判

**对齐仍可能得到 F001。** 官方将 F001 定义为风险策略不通过，F015 定义为交互失败。HTTP 200、接口调用成功、控件隐藏和本地返回“操作过一次”，都不能替代 `VerifyResult=true` 与业务认证。

**平滑拖动和固定事件节奏未稳定通过。** 试过连续缓动、去掉拖动前探测、逐字输入、暂停诊断观察器、延长会话间隔、关闭注入、普通空配置浏览器、替换驱动和免费内核等对照。部分有单次成功，多数仍出现连续 F001；没有把这些局部结果包装成稳定解决方案。

**最终有效路径是本机识别、反馈式轨迹、明确鼠标事件和累计时钟调度的组合。** 参考实测开源实现，只保留本次使用的一种轨迹分支，包含接近、停顿、加速、回拉和距离收口；通过浏览器 CDP 发送正常鼠标事件，不改服务器验证参数或结果。按累计目标时刻调度，减少把每次调用耗时重复叠加进轨迹。异常或取消时在 `finally` 释放鼠标并分离会话。

诊断对照先完成 10 次；整理进源码后又独立完成 10 次。轨迹、事件参数和调度一起变化，因此现有证据证明组合有效，尚不能断言其中某一项是 F001 的唯一原因。

## 4. 尝试过的方法：如何解读结果

| 方法 | 本次结果与结论 |
| --- | --- |
| OpenCV 透明轮廓与背景边缘匹配 | 最终使用；歧义拒猜，有本地合成回归和真实验证回执 |
| 300px 控件的二次位移标定 | 最终使用；避免手柄、拼图等速假设及拖动前探测 |
| SDK 图片就绪与两秒采集等待 | 最终保留；单独使用不足以完成连续验收 |
| 平滑缓动、逐字输入、暂停观察器、延长间隔 | 曾有个别成功或失败对照，未单独取得稳定证据 |
| 关闭脚本注入、普通空配置浏览器、替换驱动 | 诊断仍有失败，未修改公共浏览器生命周期 |
| 免费 Chromium 内核与其完整启动包装 | 仍出现 F001；仅保存在本机诊断目录，没有进入源码依赖或交付包 |
| 反馈轨迹加累计时钟调度与明确 CDP 鼠标事件 | 诊断 10 次和最终源码 10 次均完成；最终使用普通 Edge |
| 外部视觉模型、商业验证码服务 | 没有调用；没有上传凭据、图片、Cookie 或响应给求解服务 |

外部项目的通过率只用于寻找假设，不算 CourseMate 验收。免费内核另有分发许可限制，也不能因为能在本机运行就直接塞进 EXE。最后的产品实现没有依赖这个内核。

## 6. 最小复现与维护步骤

1. 先执行 `git status --short`，读交接文档和直接相关代码，核对 HEAD、标签及源码版本；保存既有修改的本机摘要。
2. Windows Python 先设置 `$env:PYTHONUTF8 = '1'`，直接运行相应测试脚本。先验证普通登录、控制识别及取消，再做真实页面。
3. 从新的空上下文开始，使用本机凭据。仅执行登录和必要的登录后跳转，不调用课程推进或考试流程。
4. 分别收集验证码回执、业务登录回执、当前会话凭证和认证页面。所有原始材料只写本机忽略目录，终端只输出脱敏结果。
5. 一轮从 1 数到 10；任何会话超时或认证未确认就结束该轮，修复后重新跑完整一轮。三次操作上限不因追求通过率而扩大。
6. 对默认窗口和最大化分别取证，记录实际尺寸；离线布局变化只验证坐标逻辑。
7. 冻结已验收源码并记录摘要。通过打包前条件后，在全新的 dist/build 子目录构建；不更新旧快捷方式，不覆盖旧包。
8. 使用原有打包测试检查新包，单独检查启动和视觉；包内验证模块与源码对应。配置、运行状态、题库、日志、截图、诊断依赖与浏览器配置目录均不得进入包。
9. 最后复查 Git 差异、基线保护、私密值扫描和许可说明。没有用户授权不提交或发布。

## 7. 后续仍需注意

- 本次证明的是指定入口和当时出现的控件变体，服务端策略或 SDK 更新后仍需重新验证。
- 连续登录成功不等于每次验证码都一次通过；本轮智慧职教就出现一次真实 F001，并在原有限重试内通过。
- 真正的数字验证码、未知安全验证、全部课程业务及整门课程端到端验收仍未完成。
- 会话隔离是认证数据隔离，不是数据加密；凭据与会话文件仍属本机私密数据。
- 诊断代码与临时依赖留在忽略目录，不作为运行依赖或能力承诺。
- 保留失败记录和未经确认的结果，比把失败会话重新编号成成功更有维护价值。

### 12.1 理解、假设、成功标准和最小步骤

本阶段起点保留 78 个非忽略文件的摘要与副本，仍是包含既有未提交改动的 `v0.2.12` 工作区。用户最初要求修复字号加减卡顿、按钮偏大、无配置首次启动 DeepSeek 地址为空；随后追加关于页 GitHub 链接可点击、三个主页面页签去掉虚线框。假设按钮外框是截图中主要需要缩小的部分，保留字符字号联动；关于页打开已有项目地址，末尾横线属于仓库名。

成功标准为连点先更新字号栏、停止后只合并应用一次全界面字号，拖动松手和保存重开仍正确；无配置、损坏配置的启动地址正确，已有自定义地址保留；关于页打开正确项目；三个页签去掉虚线且仍可用键盘切换。最小步骤为视频采帧与耗时分析、直接运行相关脚本、冻结源码、新目录构建、隔离 EXE 真实鼠标与截图复核，最后检查源码、包和本机数据边界。

### 12.2 实现与依据

原加减回调每次都同步更新全部页面字体，并在最小窗口计算中调用 `update_idletasks()`，本机源码剖析耗时约 145～421 毫秒。改为字号栏立即预览，停止点击 120 毫秒后统一更新全界面，再等待 30 毫秒让 Tk 正常处理布局后重算最小尺寸。直接调用应用字号、滑块松手时仍同步完成，并取消未执行的连点任务；保存读取当前选择值。此前源码采样的按钮回调约 0.7～11 毫秒，字号栏绘制约 14～16 毫秒。这些数值属于源码采样，不能直接当作 EXE 整窗渲染耗时或跨电脑性能保证。

加减按钮内边距由横向 10、纵向 6 调为横向 6、纵向 2，保留普通 Tk 控件及字体联动，避免重新引入第 11 节漏绘方案。本机 144 DPI、15 号字的截图中，两按钮外框均由约 62×55 缩为 54×47 像素。滑块移动时同时请求其背景和灰色滑槽重画，减少旧位置残留；逐帧采样仍见短暂重绘过渡，不能声称完全零残影或零卡顿。

DeepSeek 地址在创建变量时即初始化为现有提供方默认地址；原配置加载仍可覆盖它，因此不依赖一次服务商切换或刷新，也不覆盖自定义地址。没有修改模型列表或发起模型请求。

关于页项目地址变为蓝色、手形鼠标的链接，点击或聚焦后按回车、空格打开项目。最初调用系统默认浏览器，但本机 HTTPS 关联指向缺少打开命令的项，实际点击弹出 Windows“选择应用”，没有直接到项目页。最终复用现有浏览器检测，优先用本机已安装的 Chrome 或 Edge 打开，找不到时才交给系统默认处理；没有修改系统默认关联或课程浏览器设置。项目地址与当前 Git remote 一致，为 `https://github.com/LLL-svg-jpg/CourseMate-`。三个主页面页签只移除 `Notebook.focus` 绘制元素，保留页签的实际焦点和方向键切换；字号更新不重建该布局。

按用户建议查阅了网上和 GitHub 的一手资料。Python 文档说明 Tk 事件处理需要及时返回，Tcl 定时回调允许分步处理；本次据此合并连点更新，没有把 GUI 更新转入后台线程，也没有在回调中套一层 `update()` 事件循环。链接使用 Python 标准库，无新增依赖。参考：[Python Tkinter 线程模型](https://docs.python.org/3/library/tkinter.html#threading-model)、[Tcl 8.6 after 文档源码](https://github.com/tcltk/tcl/blob/core-8-6-branch/doc/after.n)、[TkDocs 事件循环](https://tkdocs.com/tutorial/eventloop.html)、[Python webbrowser.open](https://docs.python.org/3/library/webbrowser.html#webbrowser.open)。未找到可直接解决本机现象的确定上游补丁，没有升级 Tk 或改变全局主题。

### 12.3 本次踩坑与观察器修正

单纯去掉同步布局等待，虽然回调变短，但最小高度可能读到尚未完成的布局：曾读到 962 而实际请求高度为 1023，原布局检查出现三项失败。这一尝试撤回，保留原最小尺寸算法和原断言。字体缓存、命名字体、Windows 批量禁用重绘、换主题的私有实验没有明显降低总绘制耗时，均未加入产品。

连续点击间隔中保存整窗 PNG，会把图片编码时间混进下一次点击间隔，不能据此比较响应性能。线程发送鼠标事件也出现调度偏差；后改为独立进程按固定时刻发送，采样进程先抓图、结束后再保存。零时长按下松开并立刻把鼠标移到屏幕角落，曾丢失一次点击；另用约 12 毫秒按压、保留按钮上的鼠标位置复测，并保留原失败记录，不把“发送了六次”当作“软件处理了六次”。

截图可能被聊天窗口遮挡，旧采样中曾把遮挡误认成蓝色滑块消失；后续探针检查自己的 EXE 是否为前台窗口。移动中的连续蓝色边缘与两个分离残影也必须区分，不能只看区域宽度。最终应分别记录过渡帧和稳定结果，不要求每张屏幕抓取都是原子绘制。

本阶段还修正了自己新增的观察器错误：Tk 的 cursor 返回值需要转换为字符串；保存采样条时复用了整窗图片变量，随后在 105 像素高的采样条内查找整窗 155～260 像素区域，错误报“滑块消失”；拖动探针也曾把未稳定的蓝色边缘算入手柄中心。均对照原图后修正观察器，在新的隔离目录复测，没有修改旧验证脚本的断言或抹去失败结果。

链接鼠标探针另外踩到 ClearType 像素误判：黑色作者文字的边缘也有少量蓝像素，简单求全部蓝像素的包围盒中心，会点到作者与链接之间的空白。改为按蓝色文字密集行定位，并保留短暂按压，再检查浏览器目标地址。Windows 的 `webbrowser.open()` 返回成功也不能代替页面跳转验收：系统“选择应用”同样可能算调用成功。没有据此宣布链接通过，也没有自动接受或修改系统设置。

构建后的原首次启动检查还出现一次页面切换未生效：第二轮准备拍设置页时实际仍在 AI 页，检查按原阈值失败。保留该目录与构建失败记录，在另一全新副本中直接重跑原脚本，两轮通过；不能把第一次失败说成构建全绿。
